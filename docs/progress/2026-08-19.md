## Causa raíz real (`railway logs --build` / `--deployment`)

- `ModuleNotFoundError: No module named 'docx'` — `Root Directory=api` (el fix de ayer) hace que
  Railway copie *solo* `api/` al contenedor. El `requirements.txt` de la raíz nunca estuvo
  disponible para el build.
- Más grave: `api/main.py` importa `conductor/conductor.py` y `utils/casos.py` directo vía
  `sys.path.insert` (reuso de código, ver comentario en el archivo) — con `Root Directory=api`
  esas carpetas hermanas tampoco existen dentro del contenedor. `Root Directory=api` es
  estructuralmente incompatible con este backend, no un ajuste menor.
- Intento intermedio (`api/requirements.txt` con `-r ../requirements.txt`) confirmó esto en la
  práctica: `Could not open requirements file: /requirements.txt` — `..` no lleva a ningún lado
  útil dentro del contenedor cuando el build root es `api/`.

## Fix aplicado (commits `e064967`, `8b45111`)

- `railway.json` en la raíz — `buildCommand: pip install -r requirements.txt`,
  `startCommand: cd api && uvicorn main:app --host 0.0.0.0 --port $PORT`. Reemplaza la
  autodetección de Railpack (causa del fallo original de anteayer, antes de que Root
  Directory=api "solucionara" el síntoma equivocado) por comandos explícitos — no depende de que
  Railpack adivine bien en un monorepo con Python (raíz + `market_agent/` + `scientific_agent/`)
  y Node (`web/`) mezclados.
- `api/requirements.txt` (el intento intermedio) revertido — sin efecto una vez que Root
  Directory vuelva a la raíz, no vale la pena dejarlo como setup fantasma.

## Sebas cambió Root Directory — y aparecieron 2 problemas más, reales, hasta cerrar del todo

Sebas borró `Root Directory` en el dashboard de Railway (screenshot real) pero el cambio quedó
**staged sin aplicar** — Railway tiene un botón "Deploy" separado para confirmar cambios de
Settings, no se aplica solo. Root causa de que mi primer `railway redeploy` siguiera usando
`/api`: además, `railway redeploy` reusa el snapshot de configuración del deployment original
(capturado en su momento), no relee settings actuales — hace falta un deploy genuinamente nuevo
(dashboard "Deploy" o push a git) para que un cambio de Root Directory tome efecto.

**Problema nuevo #1 — `knowledge_module` no instalable en Railway:** una vez con Root
Directory correcto, el build instaló bien (`pip install -r requirements.txt` con el set completo:
fastapi, uvicorn, python-docx, anthropic, litellm, modal), pero el contenedor crasheaba al
arrancar: `ModuleNotFoundError: No module named 'knowledge_module'`. Causa: `knowledge_module` es
un paquete de plataforma separado (repo propio `github.com/sebasbizzi/km-knowledge-module`) que
en local se instala en editable desde una carpeta del disco de Sebas — imposible de resolver en
un contenedor de Railway. El repo además era privado (404 al pedirlo sin login). Sebas lo pasó a
público (mismo criterio que ya usó para `criza` con Vercel Hobby). Agregado a `requirements.txt`
como `git+https://github.com/sebasbizzi/km-knowledge-module.git@<commit fijo>` — pineado, no
apuntando a `main` sin fijar. Build reinstaló todo bien, contenedor arrancó:
`Uvicorn running on http://0.0.0.0:8080`. Confirmado con curl real contra
`https://criza-production.up.railway.app/casos`: 401 sin credenciales (auth de la API
funcionando), 200 con `API_AUTH_USER/PASSWORD` reales — **backend 100% en producción**.

**Problema nuevo #2 — el frontend nunca mandaba credenciales a la API:** actualizado
`NEXT_PUBLIC_API_URL` en Vercel con la URL real de Railway, redeploy del frontend, pero el login
en `criza-chi.vercel.app` (con `SITE_AUTH_USER/PASSWORD`, que además hubo que resetear porque las
que Sebas tenía guardadas ya no coincidían) tiró 500. Runtime error real (Vercel):
`API /casos respondió 401`. Diagnóstico: `web/lib/api.ts` nunca tuvo un header `Authorization` en
ningún fetch, en ninguna función — nunca se había notado porque en local, sin
`API_AUTH_USER/PASSWORD` seteadas, la API no pide nada.

Complicación real, no un simple "agregar el header": `lib/api.ts` es isomórfico — lo importan
tanto páginas server component (la home) como el client component del chat del Conductor
(`conductor/page.tsx`, corre en el browser). Meter la password de `API_AUTH` directo en el
archivo la hubiera expuesto en el Network tab de cualquiera con la sesión del sitio abierta,
anulando el propósito original de tener `API_AUTH` como capa separada de `SITE_AUTH` (la
decisión de Etapa 19 hosting). Presentado el tradeoff a Sebas (rápido-pero-expone vs.
correcto-pero-más-trabajo) — eligió explícitamente el proxy server-side.

**Fix implementado:**
- [web/app/api/backend/[...path]/route.ts](../../web/app/api/backend/%5B...path%5D/route.ts) —
  Route Handler nuevo (Next.js 16, `RouteContext` con params `await`eados, confirmado leyendo la
  doc real en `node_modules/next/dist/docs/` antes de escribir código, por la instrucción
  explícita de `web/AGENTS.md`). Reenvía a Railway agregando el `Authorization` del lado del
  servidor — nunca visible en el browser.
- `web/lib/api.ts` reescrito: en el server (`typeof window === "undefined"`) sigue pegándole
  directo a Railway con el auth armado ahí (`process.env.API_AUTH_*`, sin prefijo `NEXT_PUBLIC_`
  — Next.js lo reemplaza por `undefined` en el bundle del cliente, no hay forma de que se
  filtre). En el browser, todo pasa por el proxy propio (mismo origen) — el navegador manda solo
  las credenciales de `SITE_AUTH` que ya tiene cacheadas para ese origen (comportamiento normal
  de HTTP Basic Auth, sin código extra). `urlDescargaDocumento` (link de descarga) y
  `cerrarSesionConductorBeacon` (`sendBeacon` no soporta headers propios) van siempre por el
  proxy, sin excepción — no dependen de la rama isomórfica.
- `API_AUTH_USER`/`API_AUTH_PASSWORD` agregadas a Vercel (production, sin prefijo `NEXT_PUBLIC_`)
  con los mismos valores que ya estaban en Railway.
- `npm run build` local limpio antes de tocar producción.

**Verificado real, por Sebas mismo:** entró a `criza-chi.vercel.app` con las credenciales nuevas
de `SITE_AUTH` — "entré y funciona muy bien". Lista de casos real, chat del Conductor
respondiendo. Cadena completa confirmada de punta a punta: Vercel → proxy → Railway → Neon
producción.

## Extra, mismo día — bot de Telegram, segunda interfaz al Conductor

Con Vercel/Railway ya funcionando de punta a punta, Sebas preguntó cuánta complejidad tenía
conectar el Conductor a Telegram. Respuesta (baja-moderada: el Conductor ya expone sesiones de
chat por HTTP, el bot solo necesita un webhook nuevo que reuse esas funciones) lo decidió a
arrancar ya mismo.

**Decisiones de seguridad, explícitas con Sebas antes de codear** (`AskUserQuestion`): bot nuevo
via @BotFather (no reusar nada existente), y restringido a un solo `chat_id` — el suyo, obtenido
con @userinfobot — mismo criterio que `SITE_AUTH` en la web.

**Implementado** ([SEB-276](https://linear.app/sebabizzi/issue/SEB-276/bot-de-telegram-segunda-interfaz-al-conductor),
sub-issue de SEB-203): `POST /telegram/webhook` en `api/main.py`, reusa `conductor_sesiones` y
`_enviar_mensaje_conductor` tal cual — una sesión por `chat_id` (campo `telegram_chat_id` nuevo,
opcional, en `config/plantillas/conductor_sesiones.yaml`), encontrada como "la más reciente con
ese chat_id" en vez de por `session_id` como hace la web con localStorage. Dos capas de
seguridad: `TELEGRAM_WEBHOOK_SECRET` (Telegram lo reenvía en
`X-Telegram-Bot-Api-Secret-Token`, **falla cerrado** si no está configurado — al revés de
`API_AUTH`, que falla abierto en dev local porque ese endpoint es alcanzable desde internet en
cuanto existe) + whitelist de `TELEGRAM_ALLOWED_CHAT_ID` (mensajes de otro chat_id se ignoran en
silencio, sin confirmar que el bot existe). Ack inmediato + `BackgroundTasks`
(`_procesar_mensaje_telegram`) — una corrida de especialista real puede tardar minutos, Telegram
espera respuesta rápida al webhook, no el resultado; la respuesta real se manda aparte vía
`sendMessage`, partida en trozos de 4000 caracteres si supera el límite de Telegram. Un error se
le avisa a Sebas por el chat mismo — es el único lugar donde se entera, nadie mira logs del
server desde Telegram. `scripts/telegram_set_webhook.py` registra la URL una sola vez.

**Verificado real de punta a punta por Sebas:** `/start` + "qué hay pendiente?" en
`t.me/criza_conductor_bot` → el bot respondió con los 2 casos reales del KM.

**Extra sobre el extra, mismo día — Sebas: "le puedo subir docs?"** El webhook original solo
procesaba `message.text` — un archivo se ignoraba en silencio. Agregado a pedido: refactor de
`/archivos/extraer` (extrae pdf/docx/txt/md, Etapa 17) para compartir la lógica de extracción vía
`_extraer_texto_generico` en vez de duplicarla — el endpoint HTTP mantiene el mismo
comportamiento, confirmado sin tocar sus tests. Un `message.document` de Telegram se descarga
(`getFile` + link de descarga), se extrae igual que la web, se combina con el caption (mismo
formato que `combinarMensajeConArchivo` de `web/lib/api.ts`) y se manda al Conductor como un
mensaje más — reusa `_procesar_mensaje_telegram`, sin duplicar el manejo de sesión/respuesta.
Simplificación deliberada: sin el flujo de varios turnos de la web para "elegir a qué frente
conectarlo" (Etapa 17b) — verificado real que no hace falta: Sebas subió un PDF pidiéndole en el
mismo mensaje a qué frente conectarlo, y el Conductor lo resolvió solo con sus propias
herramientas de la costura.

**Tests:** 16 nuevos en total (`api/tests/test_main.py`) — secret ausente/incorrecto (403, falla
cerrado), update sin texto/documento, chat_id no autorizado, chat autorizado, sesión activa
