## Fix real — el Conductor no podía identificar "el último informe de cada especialista"

Sebas le preguntó al Conductor (captura real adjunta): "necesito descargar los últimos informes
de cada agente, los que hicieron con los datos actualizados de los efluentes, cómo se cuáles
son?" El Conductor no pudo responder con ids reales — solo pudo describir cualitativamente cuáles
corridas tenían datos completos, y mandó a Sebas a buscar en la web a mano.

**Diagnóstico real, no asumido:** `_tool_ver_caso` (`conductor/conductor.py`) armaba el briefing
de cada frente con `documentos_producidos: len(docs)` y `ultimo_documento: docs[-1].titulo` —
sin ids, sin fecha, sin distinguir por especialista. Peor todavía: `docs[-1]` ni siquiera era
confiablemente "el último" — `utils/casos.py::obtener_documentos_de_frente` delegaba en
`motor_api.conexiones_de` (genérico de `knowledge_module`), que no ordena por fecha ni expone
`created_at` en absoluto. El orden que se veía era el que Postgres devolviera por casualidad, no
un orden garantizado.

**Desbloqueo inmediato para Sebas** (antes de tocar código): se consultó la base directo
(`ficha.created_at`, no expuesto por `motor_api.obtener()`) para identificar con certeza los 4
informes más recientes del Frente técnico de Helios (uno por especialista, de 13 documentos
totales) y se le dieron los 4 links de descarga (`GET /documentos/{id}/descargar`) directo en el
chat.

**Fix real, no solo el desbloqueo puntual:**
- `utils/casos.py::obtener_documentos_de_frente` — reescrita para armar su propia consulta SQL
  (mismo patrón de tablas que ya usa `motor_api.conexiones_de`, con `f2.created_at` sumado y
  `ORDER BY f2.created_at ASC`). Devuelve `creado_en` (ISO) en cada documento. Anotado en el
  código y en `conductor/docs/DESIGN_GATE.md` (Decisión I) como candidato a promover a
  `knowledge_module.motor.api.conexiones_de` (parámetro `order_by` genérico) si otra instancia lo
  necesita — no se movió ahí todavía porque solo CRIZA lo pidió hasta ahora (regla de capa,
  `CLAUDE.md`).
- `conductor/conductor.py::_tool_ver_caso` — cada frente del briefing ahora incluye
  `documentos_producidos_detalle` (lista completa: id + título + agente + fecha, ordenada). La
  `nota` del briefing instruye explícitamente al Conductor a usar el último elemento de cada
  `agente` distinto para identificar "el último informe de cada especialista", y a usar el `id`
  real (nunca inventado) para armar `/documentos/{id}/descargar`.
- `api/main.py` (`GET /casos/{id}`) — de paso, cada documento en la respuesta ahora incluye
  también `agente` y `creado_en` (antes solo título/modo/estado) — mismo dato, gratis para la web
  también, no solo para el Conductor.

**Tests:** 2 tests unit nuevos en `utils/tests/test_casos.py` (mock de sesión DB con
`created_at`, lista vacía). 2 tests nuevos/actualizados en `conductor/tests/test_conductor.py`:
uno confirma que `documentos_producidos_detalle` viene bien armado, otro confirma explícitamente
que con varios documentos del mismo agente se puede identificar el último por agente (el caso
real que reportó Sebas). Un test viejo (`test_tool_ver_caso_arma_briefing_completo`) tenía un
fixture incompleto (documento sin `id`) que nunca había importado porque el código viejo no lo
necesitaba — corregido para reflejar la forma real de un `documento_caso`.

**Verificación real de punta a punta (no solo mocks):** corrida real de `_tool_ver_caso("Helios")`
contra la base de producción — identificó correctamente los mismos 4 ids (uno por especialista)
que la consulta manual directa a la base había encontrado minutos antes. Regresión completa del
backend: 539 passed, 2 skipped, 38 deselected (excluyendo `scientific_agent/` — colección rota
desde antes, módulos ya archivados que importan `tools.uniprot`/`tools.variants` que no existen
más; no relacionado con este cambio) — el único fallo real (`test_embedding_singleton`) es por
`sentence_transformers` no instalado en este entorno local, no por el código tocado hoy. `npm run
build` de `web/` limpio (no se tocó código de `web/` en este fix, chequeado por las dudas).

Decisión registrada en `conductor/docs/DESIGN_GATE.md` (Decisión I, sección 5) y estado del gate
actualizado a "Decisiones A-I".

## Continuación — sesión 2, mismo día — el diagnóstico de arriba resultó incorrecto

Sebas pidió "continuemos". Lo que las notas de arriba daban por bueno ("online, confirmado por
Sebas") no lo estaba — `railway status`/`railway logs` (vía Railway CLI, ya logueado en la
máquina, no hizo falta esperar el conector MCP que seguía sin autorizar) mostró el deployment
real en **CRASHED**, sin dominio público generado.

**Causa raíz real (`railway logs --build` / `--deployment`):**
- `ModuleNotFoundError: No module named 'docx'` — `Root Directory=api` (el fix de ayer) hace que
  Railway copie *solo* `api/` al contenedor. El `requirements.txt` de la raíz nunca estuvo
  disponible para el build.
- Más grave: `api/main.py` importa `conductor/conductor.py` y `utils/casos.py` directo vía
  `sys.path.insert` (reuso de código, ver comentario en el archivo) — con `Root Directory=api`
  esas carpetas hermanas tampoco existen dentro del contenedor. `Root Directory=api` es
  estructuralmente incompatible con este backend, no un ajuste menor.
- Intento intermedio (`api/requirements.txt` con `-r ../requirements.txt`) confirmó esto en la
  práctica: `Could not open requirements file: /requirements.txt` — `..` no lleva a ningún lado
  útil dentro del contenedor cuando el build root es `api/`.

**Fix aplicado (commits `e064967`, `8b45111`):**
- `railway.json` en la raíz — `buildCommand: pip install -r requirements.txt`,
  `startCommand: cd api && uvicorn main:app --host 0.0.0.0 --port $PORT`. Reemplaza la
  autodetección de Railpack (causa del fallo original de anteayer, antes de que Root
  Directory=api "solucionara" el síntoma equivocado) por comandos explícitos — no depende de que
  Railpack adivine bien en un monorepo con Python (raíz + `market_agent/` + `scientific_agent/`)
  y Node (`web/`) mezclados.
- `api/requirements.txt` (el intento intermedio) revertido — sin efecto una vez que Root
  Directory vuelva a la raíz, no vale la pena dejarlo como setup fantasma.

**Otros 3 gaps reales encontrados en las variables de Railway** (`railway variables`, nombres
solamente, sin exponer valores en el chat):
- Solo 8 de las 10 variables que las notas de ayer daban por subidas estaban realmente en el
  servicio — **faltaban `DATABASE_URL` y `ANTHROPIC_API_KEY`**. Sin `DATABASE_URL` la API no
  hubiera arrancado ni arreglando el resto. Cargadas ahora desde `api/.env` local (vía
  `railway variables --set`, el valor nunca apareció en el texto de los comandos — command
  substitution en el propio shell).
